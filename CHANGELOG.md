# Changelog

All notable changes to this project are documented here. Semantic versioning.

## [Unreleased]

### Added

- **`listModels` takes an injectable transport, and discovery finally has tests.** It was the most-used heylook path with no coverage at all, and the reason was structural rather than an oversight: it called the global `fetch`, nothing in the suite stubs one, and so its five throw sites were reachable only by standing up a server in each state -- while a server that is running produces exactly the one branch that needs no explaining. `fetchImpl` matches the idiom `loadModel` and `HeylookClientConfig` already carry, and the app never passes one.

  What that buys is the app's answer to the commonest heylook question. The three-way message -- the server is down, the page policy refused it, or there are no CORS headers -- names three causes because they arrive indistinguishably, as a bare `TypeError` with no status and no body. Nothing had ever checked that a failure which is *not* one of those three avoids it. `test/heylook-discovery-wire.test.ts` asserts which cause is named rather than the wording, since the message is long prose that will be reworded and anchoring on a clause would make the file a change detector for the copy. Two mutations confirm it reaches the branch selection: routing a bad status into the three-way message turns one assertion red, and passing through only `AbortError` -- the bug that once made the caller's timeout branch unreachable -- turns another red.

### Changed

- **Schema enforcement now starts off.** The owner's judgement, from reading real output, that constrained decoding costs prompt quality. It was on because that is what shipped on Gemini, and neither state was ever a verdict -- the module comment in `src/provider/shape.ts` has always said the trade runs both ways, since grammar-constrained generation buys shape conformance by distorting the token distribution while the model is writing, and prose is the product here.

  Recorded as a judgement rather than a finding, because it is one. No A/B has been run in this repo, and `ENFORCE_SCHEMA_DEFAULT` says so at the point of decision so a later reader neither mistakes it for a measurement nor reverts it as an oversight. The toggle is unchanged and per-call: turning enforcement on for a single generation is still one click, and a backend that cannot enforce still shows the control disabled rather than hidden.

  It is a named constant rather than a literal for the reason `buildClient` exists. `useState(true)` inside `useEngine` was a default nothing could reach -- flipping it broke no test and flipping it back would have broken none either, which is the wiring gap this repo keeps rediscovering. The value is now asserted, and a source-level check catches the literal being re-hardcoded; that check is named as a proxy, because reading source stands in for rendering a hook, but it is a proxy for the thing that actually goes wrong. Breakage run: restoring `useState(true)` turns it red.

  One caveat carried into `CLAUDE.md` for whoever finally runs the measurement. The unconstrained arm has a known failure of its own, recorded in `planner.ts`: a local model filling an instructional silence invented a subject sourced from reference slot 0, which `assemble` refuses. The `suppliedFacts` else-branch was written to close exactly that, but an A/B still has to score assembly failures separately from prose quality, or a defect in the off-arm will read as a verdict on decoding.


- **A sung line now has a path.** The `# Speech` block forbade naming a vocal act without supplying its words -- `sings` is in that list -- and then never said how sung words are supplied, so the only mention of singing anywhere in the prompt was a prohibition. A request carrying lyrics had nowhere to put them, and `soundscape` separately tells the model not to repeat singing there. ref 5.1 STATES the answer, "Write dialogue and lyrics as `<d>[Language] ...</d>`", and base 4.4 already treats lyrics as dialogue where one crosses a cut, so a sung line is a dialogue line: lyrics go in the beat's `dialogue` field, the singer takes a speaker id like any other voice, and two singing together take `(S1,S2)`. The block's citation is now `base 4.4, ref 5.1`, and the mixed cite was checked rather than assumed -- pointing the second part at a section that does not exist turns the citation walker red.

  The prompt says there is no separate tag for lyrics without naming the tokens, and the test asserts no denylist against them. The release declares a lyrics token pair that neither guide mentions, and a denylist would have to write those strings into the repo to test for their absence -- naming a string is how a model learns it exists. Breakage run: deleting the rule turns its assertion red.


- **The planner says who a line is spoken to, and stops under-counting beats in a fast exchange.** Prompted by a deliberately extreme specimen: eight dialogue turns across three shots in about fifteen seconds, which is roughly three times denser than anything either guide demonstrates -- both guides contain twelve `</d>` in total, and the densest single example is ref-en's three-turn coffee shop. That makes it a good probe and a bad basis for retuning a default, so the two findings it produced were taken with different standing.

  **Addressing is the substantive half.** base 4.4 STATES the slot -- "Place the speaker's identifying phrase, ID, action, and delivery outside `<d>`" -- and an addressee is reached through that action, so nothing new is being permitted. ref 5.4 SHOWS the one worked instance either guide contains, `<Subject 2> (S1) turns toward the woman and says, <d>[English] ...</d>`, and what it does with the listener is the part worth copying: she is named by visible description and given no id, because she is not speaking. The planner now says to name the addressee that way, and states that a listener never takes a speaker id -- an invented one is a vocal source the clip then has to fill, which is the failure the existing rule about naming a vocal act without words already guards. The slot is the guide's; the emphasis is house, since one instance across both guides is not evidence a model does it reliably.

  **The beat floor is structural and was taken; the density was not touched.** A beat carries at most one `dialogue` object, so N supplied lines need N beats before any action beat exists -- schema, not pacing. `recommendedBeats` now takes the supplied dialogue count and returns the larger of that and the duration figure, so it raises and never lowers. `MS_PER_BEAT` is deliberately unchanged: one extreme scene cannot retune a density, and eight turns in fifteen seconds would otherwise be advised toward six beats, steering a planner to fewer and longer speeches.

  **The word budget was not refuted, but the way it was presented was wrong.** The scene spends seventeen words against a thirty-seven word budget, which is a sparse scene rather than a wrong constant -- the figure remains an unmeasured estimate and is not cited as a finding. What it exposed is that the base path handed the model a bare number, where the Ref2VA block already carried explicit anti-padding language for ref 5.2's range. It is now stated as a ceiling and not a target, with the reason: a fast exchange is many turns and few words, so a short total is not a shortfall.

  `test/budgets.test.ts` is new, because `recommendedBeats` and `spokenWordBudget` had no coverage at all. The load-bearing assertions read the assembled prompt rather than the pure functions -- the failure this repo repeats is a correct function whose result never arrives. Breakage run: unwiring the dialogue count from `suppliedFacts` turns the reach test red and leaves the four pure-function tests green, which is the discrimination wanted. Deleting the addressing rule turns both of its assertions red and leaves the block-extraction check green. All the new prompt assertions are scoped to the block they read.


- **The `non_diegetic_music` lean is reverted to base 4.7's condition.** The planner told the model to write `N/A` unless music was asked for, on the reasoning that an invented score is a claim about the scene the user never made. That reasoning is sound and it is also symmetric, which is the part that was missed: writing a score asserts a score, and writing `N/A` asserts silence. Neither is the neutral option, so "which default" was never the question. 4.7 resolves it by declining to have one -- "Use N/A when there is no non-diegetic music" is a test applied to the scene in front of you, and a default answers it unconditionally, so every clip the planner emitted asserted it was unscored whether or not anything had evaluated that.

  `music` now mirrors the shape the `soundscape` rule two lines above already had, which was vendor-shaped the whole time: decide per scene, and use `N/A` only when the scene has no score. The population claim -- "Most scenes do not have one" -- is gone, since that sentence was what converted a per-scene test into a prior about scenes in general. `MUSIC_SENTENCE_RANGE` is untouched at 4.7's 1-3, still scoped to the music-present case.

  Corroboration, recorded because it is corroboration and not the argument: across the guides' worked examples and the three reproducible API payloads MiniMax ships, vendor practice is 2 of 8 toward `N/A`. The payloads are new evidence here -- 0 of 3 of them write `N/A` -- and the entry being reverted had weighed only the guides' 4-to-2.

  The patch prompt's rule survives unchanged and deliberately. It says an `N/A` in `music` is a judgement rather than a gap to fill, which is ordinary edit conservatism over a field whose legitimate value looks like an empty one; `music` is on `PATCHABLE_LEAVES`, so an edit is otherwise free to invent a score over a silence the planner decided on. That is not a restored default, and `reference/h3/contract.json` now says so rather than attributing the sentence to the deleted lean.

  `music-default` is removed from `notInTheGuides`, which is what turned the contract binding red and is now asserted in the negative: re-adding that id fails the suite. The breakage was run and reached the real list. The wording assertions that remain are marked as what they are: a proxy accepting "only when" or "only if", so the obvious future tidy of making the two audio rules read alike keeps the condition and stays green; and a denylist naming the two phrasings the lean actually used, which cannot be complete and says so. All three planner-side assertions are scoped to the `music` line rather than the whole prompt, because `soundscape` states its own N/A condition and its own sentence range one line up, and an unscoped assertion cannot tell which of the two it matched. Two were provably hollow: asserted prompt-wide the proxy passed on the soundscape sentence and stayed green with the lean fully restored, and the range assertion accepted `SOUNDSCAPE_SENTENCE_RANGE` while claiming to check music -- safe only because 1-4 and 1-3 differ, and false-green the moment they coincided. The two patch-prompt assertions need no scoping: `music` and `N/A` each occur exactly once there, on the same line.

  Provenance, since this rule has a contaminated neighbour: an edited copy of the base guide circulating outside this repo states a far stronger version of the lean as though it were the guide, and a prompt corpus in another repo runs harder on `N/A` than that copy's own examples do. Neither is a source for this field. The condition here comes from 4.7.


- **The contract's claims are now bound to what they describe, not merely attributed.** Every claim in `contract.json` carried two obligations and only one was enforced: it had to say where it came from (`guide` or `house: true`, checked by a walker over every leaf) and it had to say what would make it false, which was checked by a hand-written list of sixteen `it()` lines. So a claim was verified only if someone remembered to write a line for it. Nine leaves named a real exported constant -- `SLOT_ROLES`, `AUDIO_ROLES`, `CONTINUITY_PHRASES`, `DIALOGUE_TERMINALS`, `DIALOGUE_ALLOWED_PUNCTUATION`, `DIALOGUE_PLACEHOLDER`, `FRAME_ANCHOR_ROLES`, `SUBJECT_CONTENT_ROLES`, `VIDEO_STRUCTURE_ROLES` -- and were compared to nothing at all.

  This was measured before it was fixed: 63 fields of the spec were mutated to plausible-legal values and the suite run against each, and 33 of the 63 changed the spec with everything green. The sweep understated it, because it sampled one member per family and the family is not uniform -- it happened to pick `cameraTypes`, which was checked.

  Each leaf now carries `binds`, keyed by claim key so a leaf making two claims binds both (`amplitudes` binds `values` and `phrases` to different exports; the single `source` string could not say that). Four kinds: `export` compares to the constant, `render` to the serialized golden output, `quotedIn` to a pinned guide, and `unbound` records why a claim is deliberately unchecked. One generated loop replaces the sixteen lines and performs 31 export comparisons where they performed 22, guarded by a floor assertion so a resolver that skipped a claim key could not look like a passing refactor. The exemption list is pinned: `unbound` is the escape hatch, and an allowlist that grants is safe to pin because the dangerous direction is growth.

  `render` names its modes rather than scanning everything. Unscoped it would pass for almost any short string, and it would have been wrong immediately: `(S1)` occurs 14 times across the fixtures but `(S1,S2)` occurs zero times, since no fixture has two people speaking together, while the base guide states it twice. Forms the fixtures do not exercise bind to the guide instead, which is the stronger oracle anyway. The check caught one spec claim on its first run: `tags.dialogue.form` states `<d>[Language] words</d>`, which no guide contains -- base 4.4 states the rule in prose and shows filled instances -- so it is now `unbound` with that recorded.

- **Prompt blocks are checked for what they say, not only that their heading is present.** The spec described each block by heading, source, conditional, guide and note, so an instruction inside `# Audio` was semantically inverted with all 734 tests green -- the same blind spot the shape trailer has, and invisible by construction. Blocks now carry `asserts`: structural anchors only, a field name in backticks, a tag literal, a rendered shape like `[Shot N] At MM:SS.mmm, <your first beat>`. Never a sentence, because the question asked of an anchor is not "can I make this fail" but "what legitimate improvement would this wrongly reject". Eleven of seventeen blocks are anchored; the other six record in `noAnchor` why no structural anchor is reachable.

  Anchors must land in exactly one block. That rejected the first attempt at `# Recognisable people`, whose only field-shaped token is `dialogue`, shared with `# Speech` -- an anchor matching a neighbouring block would pass while pointing at the wrong text. It also guards the slicer: making the slice return the whole prompt turns that assertion red rather than leaving every anchor trivially satisfied.

- **Three defects found by the same sweep.** `sectionSeparator` was compared with `endsWith`, which accepts any suffix of the truth: with the real gap of two newlines, a spec declaring one passed on all five modes while three newlines and a wrong string failed -- and under-declaring is the direction drift takes, since someone reads the spec and changes the serializer to match. It is now an exact comparison of the gap. `shotHeader.later` was read by nothing, the pattern being a hardcoded regex, and is now derived from the spec string. `notInTheGuides` items were checked by a rule that skipped anything not starting `src/`, so the two entries phrased as prose -- `recognisable-people` and `music-default` -- were checked by nothing; items now carry a `paths` list with no prose form to fall through.

- **Two more the re-run caught, which the first pass had missed.** Re-running the sweep after the change is what found them, and both were in the plan's own text: `output.Ref2VA.summaryPrefix` declared `[`, `]` and ` + ` while the serializer built the prefix from three hardcoded strings, so the spec could say anything about any of them. Assembling the expected prefix from the spec binds all three at once. And `prompts.*.blocks[].source` was inert, so a block could claim `derived:somethingGone`: the three static kinds are now pinned and a `derived:` block has to name a function the creative module really exports.

  Where the measurements stand, stated with the commit each was taken at, because one of these numbers is easy to misread. The 33-of-63 above is the before figure. Re-running the same sweep after the binding work, but at the commit *before* this bullet's two fixes, gave 19 of 63 unnoticed. Those 19 are 11 prose fields, 3 identifiers (`invariants[].id`, `notInTheGuides.items[].id`, `version`), 3 claims declared `unbound` with a reason, and the 2 fixed here. So the figure at the current commit is 17 by subtraction rather than by measurement, and it is written that way on purpose: the sweep has not been re-run since. Separately, mutating every vocabulary claim one at a time -- 39 of them, which is the sampling error the first sweep made -- left 4 unnoticed, and those 4 are exactly the pinned `unbound` set.

- **Every guide citation resolves to a section that exists.** `output.*.guide`, `vocabulary.*.guide`, `blocks[].guide` and `sections[].guide` were all inert. 61 citations are now parsed against a small closed grammar -- the guide name is sticky across commas, so `base 4.6, 4.7` is two base citations and `base 3, ref 5` is one in each -- and resolved to a heading in the pinned file. This is what would catch an upstream renumbering, which would otherwise invalidate citations silently across the whole document at once.


- **`non_diegetic_music` now leans to `N/A`, and the lean is recorded as house preference rather than as the guide.** The planner invented a score on scenes that never asked for one, because the prompt restated base 4.7's conditional -- use `N/A` when there is no non-diegetic music -- which says nothing about which way to lean when the request is silent. It now writes `N/A` unless music is asked for or the material implies it, and 4.7's 1-3 sentence range is scoped to the case where a score is present. `MUSIC_SENTENCE_RANGE` is untouched at 4.7's 1-3, since its traceability to a guide line is the thing that makes it contract.

  **Measured after the fact, and the original claim here was too strong.** This entry first said the planner wrote a score "whenever it could imagine one", which was an assertion about a model's behaviour made without running it -- the thing this project has a rule against. `scripts/music-lean-heylook.mjs` runs the comparison: the same ideas through the shipped prompt and through the exact wording it replaced, on a local 26B, three conditions.

  On plain scenes -- a locksmith cutting a key, a chef plating a dish -- both wordings answered `N/A` 6 of 6. The old wording was not writing a score there at all. On scenes that ask for one, both wrote a score 4 of 4, so the lean suppresses nothing that was requested. The difference is confined to the atmospheric middle, a rooftop at night, a goodbye at an airport gate: the shipped prompt answered `N/A` 17 of 18, the prior wording 9 of 17, with the direction consistent across all three replications. So the effect is real and roughly a doubling, but it exists only in the band where a model is guessing, which is narrower than what this entry originally claimed.

  Scope, since it is easy to over-read: one local model, not the shipped Gemini default, which has no key on this machine and is still unmeasured. The atmospheric ideas were chosen by hand because they were expected to discriminate, so they bound the direction of the effect and not its size in ordinary use.

  This runs mildly against the guides' own example distribution, four scores to two `N/A` across the two files, so it is preference and is declared as `music-default` in `notInTheGuides` with that stated. A near-identical but stronger rule -- `N/A` as the normal answer, one sentence rather than 1-3, with unsourced hit-rate figures -- appears in the annotated copy of the base guide that `reference/h3/README.md` describes, and none of that is adopted.

  The rule reaches the patch prompt too, which said nothing about music at all. `music` is on `PATCHABLE_LEAVES`, so an assisted edit was free to invent a score over an `N/A` the planner deliberately wrote -- the same asymmetry the negation rule already carries. The breakage was run against the half that crosses an assembly step: deleting the patch sentence turns one assertion red, and it fails on `/music/`, which is what confirms the field was previously unmentioned there. The planner assertion on the lean is a wording proxy and says so in the test, because no rendered shape distinguishes a default from 4.7's conditional.

  The contract test could not have caught any of this on its own: it indexes prompt blocks by heading, and the whole change lives inside `# Audio` and `# Rules`. That is the same blind spot the shape trailer has, and the new assertions are the control.

- **The guide pins have a second, independent instance to check against.** MiniMax ships both tracked guides as the `references/` of its own `h3-prompt-writing` skill; each hashes to the value already recorded in `contract.sources`. The pin was previously only checkable against itself. What ships around them is not contract, and the longer of that skill's two copies carries added tips of which one is unsupported by either guide and one is contradicted by the base guide's own worked examples -- the padded-copy pattern, in first-party material.


### Fixed

- **Two direct edits in the same tick lost one of them and forked the history.** Each read the document from the render it started in, derived a new one, and wrote it across three IndexedDB round trips; the second computed from the document the first had already replaced, so the first vanished from the head document while its version stayed in the tree -- parented beside the second rather than before it. Both halves were measured against the running app, by blurring two fields in one tick: before, the soundscape edit was gone from storage and `v0019`/`v0020` both named `v0018` as parent; after, both edits are in the document and the chain is linear.

  Two changes, and neither works without the other. Direct edits go through a serial queue that reads the document *when the task runs* rather than when it was queued, so the second composes on the first. And `commit` takes its parent from a ref it also writes, rather than from the render's `headVersionId`, because two commits in one render named the same parent even once the documents were correct.

  The refs are maintained twice over, which is deliberate and is the thing to read before simplifying it: effects on `doc` and `headVersionId` catch every path that sets them, including the ones that never touch `commit` -- a load, a checkout, an erase -- and the writes inside `commit` catch what an effect cannot, since a queued task can run before React has rendered and a ref waiting on a render would hand it the document its predecessor already replaced.

  The queue itself is `src/ui/queue.ts` rather than a few lines inside the hook, for the reason this repo keeps rediscovering: there is no React renderer in the devDependencies, so a guard written inline is one nothing can reach. `test/queue.test.ts` asserts the properties the edits actually need -- one at a time, in the order handed over, and a rejected task neither strands the queue nor swallows its own error. That last one matters most: a stalled queue would mean one throwing edit silently eating every edit after it.

  What this does not change is the earlier measurement. At human cadence -- 250/100/50/20/5ms between edits -- the edits already chained, and only a driver at 0ms forked them. It is a correctness fix for a window a person is unlikely to hit, which is why it stayed unfixed once already, with the reasoning recorded rather than the behaviour changed.

- **A line you typed yourself could not be edited by anyone, including you.** Gate 3 refuses a patch to `dialogue.text` when `userSupplied` is set, with the reason "Edit it directly instead" -- advice that was impossible to follow, because a typed edit goes through the same `applyPatch`. The editor offered the field, labelled it "yours - locked to models", and refused every keystroke that reached it. `applyPatch` now takes an origin, defaulting to `model` so a caller that says nothing keeps the protection, and `editDirect` is the one caller that says `direct`. The gate is unchanged for the case it exists for: the model still cannot touch the line. Two mutations, opposite directions: dropping the origin check reddens the retype case, defaulting the origin to `direct` reddens the model refusal.

  Found by review of the previous commit rather than by using the app, and it was a bug before that commit -- but the mark made it permanent rather than transient, which is how it surfaced. That is the second time in two days that a mark or a seed turned an old silent failure into a visible one.

- **A refused field could not be un-refused by fixing it.** Retyping the value the document already holds is the obvious way out of a refusal, and it hit `Field`'s `draft === value` early return, which left the mark on. Nothing could clear it: the `[value]` effect needs `value` to change, and it had not. `CutField` in the same commit handled that branch correctly, which is the tell -- one state machine, two answers, written minutes apart.

- **A banner outlived the edit that fixed it.** `applyDirect` never cleared `error`, though `generate` and `applyAssisted` both do on entry, so a rejection stayed on screen after a successful correction -- the field saying the value was in the document while the banner said it was not. It clears on the next commit attempt now. The narrower case stays and is deliberate: retyping the stored value clears the field's mark without attempting a commit, so the banner remains until dismissed or superseded. The mark is per-field state; the banner is the last thing that happened.

- **`coerceToLeaf` asked the stored value what kind of leaf it was.** `Array.isArray(before)` decided whether to split a list, one line above a numeric branch that asks the schema. Since `loadDocument` reports rather than gates, a document holding a non-array in `visibleText` opens -- and could then never be repaired through the editor or a model patch, because the split was skipped and the raw string refused. Both branches read the schema now.

- **A comment claimed a guard it does not have.** `applyDirect`'s `busy` check reads as though it serialises direct edits against each other; nothing in that function sets `busy`, so it sees a generation or an assisted edit and never a second direct edit. The overlapping case remains what the measurement said it was -- a window under one IndexedDB round trip, chained at every human cadence tested and forked only at 0ms -- but it is worse than before in one respect worth writing down: the discarded edit's `applyDirect` returned true, so its field will not mark itself. The comment says all of that now, including that the fix would be reading the newest document rather than the render's.

- **A field whose edit the document refused went on looking committed.** The draft lived in the field and the write happened somewhere else, so every path that did not commit -- the busy drop, a rejection from any of the four patch gates, a throw -- left the typed text sitting in the box as though it were in the document. The error banner said something was wrong; it did not say *which field*, and with several fields on screen that is not the same information.

  `applyDirect` now answers whether the document took the value, and a field whose commit came back false marks itself: an amber ring and "not in the document" beside its label, cleared the moment a value arrives from the document. Deliberately a mark rather than a revert -- reverting is defensible for a four-digit cut time and destroys a paragraph of prose, and these are the same component. Checked in the app on both: emptying a dialogue line (refused by the shape gate at `>=1 characters`) and typing a fractional cut time each leave the field ringed, the document untouched, and -- for the cut time -- the readout still showing what the document actually holds.

  The mark also settles what the previous entry left open. Reporting the busy drop as a banner explained the divergence; this removes it.

- **The model half of the shape gate is now checked where it lives, not just where it is defined.** `test/leaf.test.ts` asserts at `applyPatch` that a numeric leaf reads its number out of a model's text. Whether an assisted edit *reaches* that code is the wiring question this repo keeps rediscovering, and it needed no provider: `test/pipeline-provider.test.ts` already drives the real `edit()` through a client that implements `InferenceClient` rather than mocking an SDK, so the reply is a fixture. Two cases -- `"6200"` applies as the number `6200`, `"6200.5"` is refused and names the field. Disabling the coercion reddens the first, which is what says the pipeline path reaches it.

- **A patch could write a value the document schema rejects, from either direction.** `PATCHABLE_LEAVES` says where a write may land. Nothing said what may land there, and the hole was live on both paths into it: the editor committed whatever `Number()` returned for a cut time, so typing `7100.5` stored a fractional millisecond; and a patch operation carries `value: string`, so an assisted edit of the same field would have written the string `"5200"` -- that half is asserted at the gate rather than run against a model, which is the level of evidence the claim rests on. Either way the document saved, serialized, and validated clean -- the validator has no opinion on the *type* of a value -- and then failed `H3DocumentSchema` on the next load, putting a "does not match this build's schema" notice on every open for a value the app itself had written. Measured, not reasoned about: `7100.5` typed into the running app produced exactly that notice, naming `shots.1.cutAtMs`.

  `applyPatch` now has a fourth gate. `src/core/ir/leaf.ts` walks `H3DocumentSchema` for the shape of the leaf being written, and a value that shape rejects is refused with a reason instead of stored. The shapes are walked rather than tabulated on purpose: a second table of field types is a table that drifts from the first, and this way `shots[].cutAtMs` is an int at or above zero because the schema says so once. The same walk gives the model's string value a home -- a numeric leaf reads its number out of the text, so an assisted edit applies `5200` rather than `"5200"` -- while an empty string is deliberately left alone to be refused, since `Number('')` is 0 and that is a cut at the start of the video.

  This subsumes a crash rather than merely a typo. A negative cut time reached `formatTimestamp`, which throws rather than renders below zero, out through `serialize` inside `editDirect`; `App.tsx` calls `applyDirect` as `void`, so it landed as an unhandled rejection -- no banner, no version, a field that appeared to do nothing. `applyDirect` now reports a throw instead of dropping it, and reports the edit it discards while a generation is running rather than discarding it in silence. Confirmed in the app: `-200` is refused with `Too small: expected number to be >=0`, nothing is written, and the console stays clean.

  The suite gains `test/leaf.test.ts`. One assertion is the property rather than a case -- every entry on the allowlist resolves to a shape, so a leaf added without one cannot silently become a write surface that refuses everything. Three mutations, each landing where predicted: disabling the gate turns five assertions red, dropping the numeric coercion turns two red (including the model-sends-text case), and seeding the editor's draft from the displayed value again turns two red.

- **Tabbing through the cut-time field of a shot that had none committed a cut at zero.** Introduced by the commit above and found by an independent review of its diff, not by any check in it. The draft seeded from what the input displays -- `value ?? 0` -- so on a shot carrying a live `SHOT_MISSING_TIMESTAMP` the field already held `"0"` with nothing typed, and blur wrote it. That erased the diagnostic, wrote a `[Shot 2] At 00:00.000` nobody asked for, and left a document that validates clean with nothing to say what happened. The old keystroke-committing input could not do this, because `onChange` needs a keystroke.

  `cutDraft` is now empty for a missing cut time, and the readout beside it says "no cut time yet" rather than `00:00.000`. The test that matters is neither of the two obvious ones: it asserts that for every value including `null` and `0`, a draft nobody touched commits nothing -- the property the two halves have to agree on, rather than a sample of it.

  Verified against a document seeded into that state rather than one this build wrote: focus and blur left the cut time null, the diagnostic standing, and the version count unmoved.

- **The cut time wrote a version per keystroke.** Every other typed field in the editor commits on blur, for the reason stated next to `Field`: a commit is a version, and per-character commits bury the branch tree. The cut-time input was the one that did not -- it committed straight from `onChange`, so a four-digit value left four entries in the history. Measured rather than reasoned about, since nothing in the suite can see this: seven versions before typing `6300` one digit at a time into shot 2, eleven after, the four new ones all labelled `Edited shots[1].cutAtMs`. That is also what makes the fix checkable -- one version for the same gesture afterwards is a claim about a number that was actually counted first.

  It is now a draft committed on blur, with Enter blurring rather than committing so that blur stays the single write path, and the `ms = ...` readout reading the committed value rather than the draft -- it stops moving until the write lands, which is the commit made visible for free. The draft is a string, so backspacing to empty is representable; a numeric draft turns an empty field into `0` and fights whoever is typing.

  The decision of what a blurred draft writes is `cutCommit`, exported and tested, because there is no React renderer in the devDependencies and both of the traps in it are silent. `Number('')` is `0`, so clearing the field and blurring would have written a cut at the start of the video; and the comparison has to read the stored value rather than the `?? 0` the input displays, since a shot after the first with no cut time is a live `SHOT_MISSING_TIMESTAMP` and typing `0` into it is a real change. Range and ordering are deliberately not re-checked here -- `validate/rules/timeline.ts` owns them, and a second opinion in the editor would be a warning severity wearing a different hat. Two mutations confirm the test reaches the subject, each narrow: parsing with a bare `Number` turns the empty and non-numeric assertions red, and comparing against `current ?? 0` turns the missing-timestamp one red.

  Confirmed in the running app: four keystrokes with no version and the readout still on the old value, then one version on Enter; a cleared field blurred back to the committed value with nothing written and no error; and a focus-and-blur with no edit writing nothing on a shot that already carried a cut time, where committing an unchanged value would have surfaced `applyPatch`'s "Value is unchanged." rejection as an error banner. That last check is narrower than it first reads, and the case it leaves out is the one that broke: on a shot with *no* cut time the same gesture did write. See the entry below.

- **A discovery reply could describe a machine you had switched away from, and a failed one never healed.** Two defects in `refreshHeylookModels` from one missing idea, and the second was the worse of them. The roster, the error and the "asking ..." indicator were three separate `useState` slots written independently at the end of an async call, so a reply arriving after an instance switch overwrote any subset of them -- the picker listing one machine's models while every call went to another. The write that outlived the session was the one nobody had counted: a stale roster reached `setSetting(HEYLOOK_MODEL_SETTING, ...)` and persisted a model id chosen from the wrong machine's list, which came back on the next load as a selection that machine may never have served.

  The error path was separately sticky in the wrong direction. It wrote `[]` while the re-discovery effect gated on `!= null`, so a failure both satisfied the gate and meant nothing was there: a server that was still starting up produced an empty roster that could only be recovered with the refresh button, which sits inside the panel reporting the failure. `unasked` and `failed` are now two states rather than one value doing both jobs.

  The three slots are one `RosterState` that names the instance it describes, and the transitions moved to `src/provider/heylook/discovery.ts` as a pure function. That is the point rather than tidiness: there is no React renderer in the devDependencies, so a guard written inline in the hook is one nothing can reach -- delete it and the suite stays green and the screen looks right. `test/discovery.test.ts` asserts the table instead, and three mutations were run to confirm it reaches the subject: dropping the instance compare turns two assertions red, letting `failed` satisfy the gate turns two red, and accepting an outcome with no ask in flight turns one red. Each was narrow rather than suite-wide.

  A failure is now cleared by a gesture -- the refresh button, switching machine, or selecting heylook in the provider picker -- never by the effect that depends on the state, which would be an unbounded retry against a machine that is down.

  One guard stays unreachable and is named in the code rather than left to be found: the side effects of a resolved discovery (the notice, the selected model, the persisted row) are gated on a ref, because the reducer cannot un-persist a write. That ref is maintained by an effect on the instance state rather than by `setInstanceId`, since the settings restore calls `setInstanceIdState` directly -- a ref written by the setter alone would still name the default instance after a restore and would then discard every discovery for the restored machine as stale.

  Checked in the running app against the live server and two deliberately broken origins, since none of the above is reachable from the suite: a discovery held in flight against a blackholed address, the instance switched back to the live machine, and the stale timeout arriving 20 seconds later left the roster, the picker, the error line and the stored `heylook-model` row all describing the machine actually selected -- while still being traced, because the log records what happened on the wire. The failure case asked exactly once over seven seconds rather than looping, and a stub server brought up on the previously refused port was picked up by the provider-picker gesture with no reload.

### Added

- **A pre-flight load when a heylook model is selected.** `POST /v1/models/{id}/load` runs before the response of the generate that would otherwise trigger it, and while a model loads there is nothing on the connection at all -- no headers, no first chunk, no keepalive. Streaming would not help, because the stream has not started, so a non-streaming client cannot tell a loading model from a hung server. The header now says `loading <model>...` for as long as it takes. Measured against the live server: a cold 27B took 6.4s, a cold 15GB bf16 3.81s, and the same id already resident answered in 1.4ms, which is why this is a pre-flight and not a cost.

  `?warm=true` is deliberately not sent -- it additionally runs a one-token generation, which takes the generation gate and can queue behind another request's long run, turning a pre-flight into the unbounded wait it exists to remove. Nothing about the call can fail the selection: every outcome is a notice, because a decoration that breaks what it decorates is worse than no decoration.

### Fixed

- **Version ids are allocated inside the transaction that writes them.** The previous fix read the highest id in one call and wrote in another, justified on the app issuing one model call at a time. That justification was false: `applyDirect` had no in-flight guard, so two direct edits could each resolve the same id and the second `put` would destroy the first version row -- the counter bug again, in a narrower window. A review found it before the race did. The scan and the write now share one readwrite transaction, so the guarantee holds whoever calls it, and `applyDirect` gained the guard `applyAssisted` already documented.

- **An erase left the policy overrides in memory, and the next edit wrote them back.** `erase` deletes the `settings` store, which holds them; `resetAfterErase` reset provider, model, key and document and not those. So touching any policy control afterwards restored the erased overrides to storage, while the panel went on reporting "this machine" for a value storage no longer held -- exactly the failure the comment three lines above it was added to prevent.

- **Writing one machine's override destroyed another machine's unreadable one.** The write path round-tripped the *parsed* bag, and parsing keeps only what validates -- so an override this build rejects was dropped from storage permanently the next time any other machine was edited, while the load site's comment promised in as many words that such entries are kept. Writes now merge one attribute into the raw stored value. Taking one attribute rather than a whole policy also removes the stale-bag class: a caller holding an older copy can no longer drop a sibling written moments earlier.

- **The settings panel validated on read and not on write.** It was the only writer and enforced neither the declared floor nor integer-ness, so typing `-5` into the retry budget stored `-5000`: a deadline already in the past, handed to the client for the rest of the session, then rejected on the next load -- where it presented as storage being corrupt rather than as the control that wrote it. Validation moved to the write boundary, where the same derived validators already guarded the read, and a refused value is now reported at the moment it is refused.

- **The model pre-flight could throw, and could speak for a selection that no longer existed.** `response.text()` sat outside the guarded region, so a connection dropped after the headers rejected out of a `void`ed async block with nothing to handle it -- while the function's own contract said it never throws. And a slow load finishing after a newer selection cleared the newer one's indicator and posted a notice naming the model the user had moved off. Both guarded; the contract now names its one deliberate exception, an abort.

- **A version id counter that reset on every page load, overwriting history.** `nextId` was a module-level `let counter = 0`, documented as "monotonic, collision-free within a session". Both halves were true and the qualifier was the bug: `put` overwrites by key, so the first version recorded after any reload was written to `v0001`, on top of whatever `v0001` already held. One version destroyed per reload, silently, with the loss invisible until someone went looking for the root of their own history. Ids now continue from what storage holds, which is the only thing that knows what has been used. Verified in the running app against a live model: a real generation recorded `workspace:v0007` beside six existing versions rather than landing on `v0001`.

- **A damaged history rendered as no history at all.** The same counter bug wrote a version whose `parentId` was its own id, because the head being replaced was the id being written. `buildTree` had no cycle guard, so that node was never pushed to `roots` and became its own child -- and with the rest of the history chained beneath it the root list came out empty and the panel said "No versions yet" over six stored versions. A version inside a parent cycle is now treated as an orphan and shown, which is the rule the surrounding code already stated for versions whose parent was deleted. The write bug is fixed above; this stays because the damaged rows are still on disk and because a cycle must degrade to something visible.

  The first cycle check was wrong in a way worth keeping: it reported every node *descended* from a cycle as being in one, which detached the whole tree into separate roots. A test caught it, and the red said what the check had encoded rather than what it was meant to.

- **A busy `/load` was reported as a missing model.** On server 1.79.52 the two routes answer the same condition with different codes -- `/v1/messages` gives 503 with `Retry-After`, while `/v1/models/{id}/load` gives **500** carrying `MODEL_BUSY: cannot make room -- [<id>] is generating`. Classifying on the status alone sent a transient, self-clearing wait down the branch whose advice is to refresh the model roster, which was confidently wrong: the roster was fine. The token decides it now, because 500 on that route is also the genuine "that model failed to load". Both codes were measured against the live server within a minute of each other, and the bug was found by clicking rather than by any test.

  Reported upstream and fixed there in 1.79.53, which aligns that route on 503 with the same envelope as the rest -- measured on that build once it was running, rather than left on their account. Both branches are kept deliberately: the status matches .53 and after, the token matches below it, and the token cannot be replaced by treating 500 as busy, because on that route 500 is also the real load failure.

### Fixed

- **The retry-budget input rewrote what you typed.** Seconds are shown and milliseconds are stored, and the input's value was recomputed from the stored number on every keystroke -- so each character was committed, converted up, and read back longer for the next one to append to. Typing `60` over `300` stored 3000000 ms. The row now holds a draft while it is being edited and re-reads the resolved value on blur, which also makes a refused override visibly snap back to what is actually stored. No test in the suite could have caught it: the round trip only exists on screen, and it was found by typing into the box.
- **`--color-fg` is named rather than copied.** The settings panel needed the ordinary foreground colour to lift a value out of muted surroundings, and `body` carried it as a literal. Defined once in `src/index.css` and read by both.
- **The backpressure retry gave up on the one condition the server documents as normal.** Three attempts against a `Retry-After: 1` header is four seconds, and the live server sends that header with the message "is generating -- wait for it to finish" while a generation runs for minutes. The header is a poll interval, not a completion estimate. The budget is now five minutes of wall-clock with exponential backoff and the header as a floor. Found by probing a running server, not by reading the code, and confirmed by occupying it and watching a second call queue for 107 seconds and then succeed.
- **A negative `Retry-After` turned a queue into a busy loop.** `Date.parse("-1")` succeeds as a year, so a numeric header that failed the seconds check fell through to the date branch and became a zero wait against a server that had just said it was saturated. A numeric header is now decided by the numeric branch alone. Found by a test written to assert the fallback, not by reading the code.
- **JSON extraction took the first parseable object rather than the longest.** A preamble saying "the schema uses `{}` for an empty object" in front of a real reply yields `{}` — valid JSON, parses cleanly, and then fails `PlannerOutputSchema.safeParse` with a message about a missing field rather than about the wrong object having been picked. Coverage keyed by slot, so one entry cleared both labels and nothing reported the loss. The marker-class rule treated any slot carrying a Video label as visual-only, making `fully_copy` on the audio line — the correct ref 4.2 marker and ref 2.5's own example — an error with no way to satisfy it. And `subject_definitions` read one description per slot, so the same sentence rendered twice, once describing a video under an Audio label. `RetentionTarget.labelKind` and `ReferenceSlot.audioDescription` are both optional, so documents written before them keep loading and mean the primary label, which is what all of them have. The planner already returns the two kinds in separate fields, so `assemble` knows the kind and nothing downstream infers it.

- **The contract covers what the code exports, in both directions.** Every check bound what the spec declared against the code; nothing looked the other way, so an omission was invisible rather than a disagreement. `SLOT_ROLES` and four role partitions were absent entirely — 19 values deciding which label kind every reference asset gets and whether it earns a definition line — along with the continuity phrasings, both dialogue punctuation sets and the house `<d/>` token. Each vocabulary leaf now names the constant it describes, and a constant that lives elsewhere in the spec is listed by name rather than left to a substring match.
- **Every prompt block says where it came from, with the same key the vocabulary uses.** The blocks are where house rules are actually written into the model's instructions and they were the least attributed part of the spec: one marked `origin: "house"`, five with nothing, and the patch prompt with nothing on any block. `MODE_SLOT_MISMATCH` was cited to base 1, which describes what each mode is and states no cardinalities at all — the counts it enforces are house policy. The `$schema` pointer named a file that has never existed.
- **`CAMERA_PROSE_HINTS` is gone.** A table of verb forms per camera motion whose comment claimed the validator used it to confirm the prose expressed the annotated motion. No such rule was ever written, and writing one is the prose pattern-matching this project purged seventeen rules of — "the camera holds" and "the frame stays put" are both a static shot. `DIALOGUE_TERMINALS` and `DIALOGUE_ALLOWED_PUNCTUATION` were dead beside it while the rule that needed them hardcoded its own; they are wired up now, which also removes the disagreement between the constant and the message it produced.

- **Four validator rules had a green half that was handed nothing to look at.** Every control asserts its code is absent from known-good input, which is the cry-wolf check — and the five golden fixtures contain no voiceover, no on-screen text, no line crossing a cut and no truncated speech, so `VOICEOVER_PHRASE_MISSING`, `VISIBLE_TEXT_NOT_QUOTED`, `SCENETRANS_UNPAIRED` and `CUTOFF_NOT_AT_END` were asserting silence about features nothing exercised. `test/fixtures/exercised.ts` fills the gap with four documents that validate clean and are deliberately not golden, since the goldens must stay byte-exact reproductions.
- **`Control.inspects` is required, so a rule cannot ship with a hollow green.** One predicate per code naming the input class its rule examines, checked against the fixture the green half runs on — the same shape as the control-coverage meta-test that refuses a code with no red. Its honest limit is stated where it lives: it proves the corpus holds an input the rule inspects, not one that would expose the rule's bug. It would not have caught the `userSupplied` scoping error, because the corpus does carry a supplied line and the rule was rightly silent about it.

### Removed

- **The fifteen presets, and the mode they lived in.** Each asserted that a particular pairing of four pack ids was worth having, and none had ever been checked against real H3 output — a name on an unverified guess borrows authority it has not earned. Directed mode picks the same four things and wild draws them behind an actual leverage test. `'exploratory'` stays in the stored union because documents written under it exist; it restores as `directed`, which is what it always was underneath, and a control proves both halves of that.

### Changed

- **`test/guide-fidelity.test.ts` says what it does not establish.** Both of its checks look only at the five worked examples, so a copy of the base guide with its field descriptions rewritten around intact examples passes every assertion in the file — one was tried, and all four base-guide fixtures matched it byte for byte. What separates such a copy from the official text is the sha256 pin in `contract.sources`. The header now says so, so the pin is not relaxed later on the grounds that fidelity covers it.
- **The glitch mode notes assert the property instead of five sentences.** Each mode's note was pinned by a specific sentence, which measured the wording rather than the thing that matters: that every mode is told something different and told only its own. The notes are read out of the table now, so a reword is invisible to the test and a copy-pasted note is fatal to it. Proven all three ways — red when two modes share a note, red when the lookup is hardcoded to one mode, and green when a note is reworded to say the same thing, which is the case the old test got wrong.
- **A test that breaks whenever the logic changes is a change detector, not a test.** The other half of the red/green rule, and the more common failure: proving a check can go red establishes only that it is coupled to the line you edited. What makes a red informative is that the test would not have fired for a legitimate change to the same code. Evidence from this session — an assertion pinned the exact sentence `do not add a full stop it does not have`, and it failed when a parallel clone reworded that instruction to say the same thing better. The prompt assertions with a real anchor now use it: the rendered shape `[Shot 1] <style>, <your first beat>`, field names, tag literals, and pack directives read out of the table rather than copied from it. The ones with no anchor say in the test that they are wording proxies.
- **The red/green rule says where a breakage earns itself.** It read "a check is unverified until it has been shown to go red for the right reason", which is true and, taken as a ritual, produces theatre: changing a constant to watch its own equality assertion fail proves nothing and trains you to read "went red" as "is sound". The question a breakage answers is whether the check reaches its subject, so it belongs where a green could come from never arriving — across a schema, a barrel, an assembly step, a UI path, or beside a second guard that could be carrying the assertion alone. That is not licence to skip it: deleting the creative-mode stamping from `compile` left the whole suite green because it sat past the model call, and `{setting}` versus `{setting:random}` had no control at all under a describe block whose name said the case was covered.
- **A red is information about the check, not a pass mark.** From an axis check written in another clone: its first version went red against nine packs that correctly claim no axis, and the failure was the check encoding a property that sounded right rather than the one the table has. Recorded in `CLAUDE.md`, with the same point carried into `VISION.md` and the header of `test/validate.test.ts` — which is the case where a breakage plainly does earn itself, since a diagnostic nothing can make fire is decoration.

- **A creative selection travels; its directive text does not.** `CompileInput.style`, which carried a resolved envelope of prompt text plus the inputs that produced it through eight files, is now `CompileInput.creativeMode` carrying only the mode and the pack ids. The planner and patch prompts each derive the directive themselves, from the same record through the same function. Before, one path was handed pre-resolved text and the other built a different shape by hand, which is how the two would have drifted apart.
- **The pack tables are the single source for their family.** Ids, names, directives and strength axes now come out of one array per family, with the id union derived from the data the way `vocab.ts` does it. Adding a pack was a three-place edit across two files; it is now one place, and a pack cannot exist without a score.
- **Reference anchors have string ids (`R01`-`R30`) and share one id space with the packs.** The `string | number` union behind them was the sole cause of three separate branches — a `typeof` fork in the scorer, a `z.union` in the schema, and two-branch handling in the resolver. A stored document naming an anchor by its old number resolves to no style rather than failing to open.
- **The creative picker holds no state of its own.** The selection lives in `useEngine` and the panel is driven by it. Checked in a browser against a seeded document: the four dropdowns come back with the stored selection, and changing one preserves the other three.
- **The module exports only what something calls.** `wildPresets` and `getPreset` were defined, exported and — in the first case — tested, with no caller anywhere; `getAnchor` and `getVisualPack` were superseded by the single `getVisual` lookup the moment packs and anchors shared an id space; `activeAxes` is used only by the rule beside it and is no longer exported. Four are gone; the fifth stopped being public. This is the same shape as the dead schema fixed below, found by looking for it after.
- **The picker says when it describes the next generation rather than the open document.** The two carry different facts — what the next generate will use, and what the current prose was written under, which is what an assisted edit preserves. Changing the picker without regenerating left the badge and the patch prompt saying different things with nothing to indicate it.
- **A restored selection drops pack ids this build no longer has.** `pruneSelection` runs where a stored record enters the UI. The derivations already skipped an unresolvable id, but left in the selection it rendered as a blank dropdown and rode along through every later edit without ever being visible.
- **Strength is a scope, not a volume knob.** Each level states its own authority over the request, and the core planner instruction defers to the section rather than claiming a blanket override — `subtle` previously said to keep the treatment grounded while the core prompt said the direction overrode the request, in the same prompt.


- **`device` key mode is decrypt-only.** It derived the AES key from `navigator.userAgent + navigator.language`, which is public. Existing envelopes still open, so nobody loses a stored key, and the next save upgrades them to `origin`. A stored key that cannot be decrypted at all is now cleared rather than left in place claiming a key exists that will never open.
- **`DB_VERSION` removed.** Nothing read it once the schema, rather than the version number, became the test for what exists. Keeping an exported constant that no longer governs anything invites someone to open at it.
- **`fake-indexeddb` is a devDependency again.** It was dropped in 0.3.0 as unused; the storage tests need a real IndexedDB implementation rather than a mock. Dev-only, so the five packages reaching the bundle are unchanged.
- **README and CLAUDE.md both state what this is**: one person tinkering, no roadmap, no support, no reviewers, possibly no users.
- **Security section rewritten.** It is now a short statement of what is stored, where, and what leaves the machine, and says plainly that this is a personal-tool posture and wrong for anything shared. Detail moved to a new **Under the hood** section at the end, which states the sample size of its own checks: one browser, one machine, by hand.
- **Claims cut back to what the evidence supports.** "Interactions are never stored server-side" conflated `store: false` with Google-side retention generally; the flag opts out of Interactions conversation-state storage and nothing more, while abuse-monitoring logging and free-tier product-improvement terms apply regardless. Dependencies are now described as trusted rather than audited.
- **Layout section said the database has five stores.** It has three: `documents`, `versions`, `settings`.

### Fixed

- **A restored directed selection was invisible and the first change destroyed it.** The picker held the four pack choices in its own state, initialised empty. After a reload the badge showed the stored style but every dropdown was blank, and changing any one of them read the empty local copy, found no visual medium, and silently cleared the style. Presets and wild rehydrated correctly, which is what made it easy to miss. The panel is now driven entirely by the record passed in, so there is one copy rather than two.
- **A document written with a reference anchor selected would not parse.** Anchors moving to string ids narrowed the stored `visual` field to a string, and every document carrying the old numeric form then failed the new schema check, showed a notice on every load, and had its style silently dropped. `getVisual` now understands both forms and `pruneSelection` rewrites the old one, so such a document opens clean and comes back with its anchor. This is precisely the tightening the rule added in the same change forbids; it was caught by review, and the control that would have caught it is now in `test/creative-integration.test.ts`.
- **A schema notice could bury the notice saying the stored API key was gone.** Both are set in the same effect and the second overwrote the first, so a browser that failed to decrypt the key and failed to parse the document reported only the document. They are concatenated now.
- **`H3DocumentSchema` was dead code.** It was defined, exported, maintained, and imported nowhere, so nothing validated a stored document and the round-trip safety it was described as providing did not exist. It is now checked at the load boundary and reports rather than gates: a document that fails to parse is still opened, with the offending path surfaced as a notice, because a build that refuses to open what the previous build wrote loses work that exists nowhere else. Confirmed in a browser as well as in tests — a hand-damaged document opens, keeps its shots and its creative mode, and names its own defect.


- **The same wedge in the document database.** `H3TransformationEngine` opened at a hardcoded version 1 with unconditional `createObjectStore`, so a database that already existed at version 1 without its stores never got them and every call threw `NotFoundError`. It now opens without naming a version and treats the stores *and their indexes* as the test — a `versions` store missing its `documentId` index breaks the history view exactly as silently as a missing store. Repair creates only what is absent, so existing rows survive; `test/db.test.ts` asserts that rather than assuming it. Three controls confirmed the tests go red: restoring the fixed-version open, dropping the index check, and removing the create guards. Also checked in Chrome against a hand-wedged database carrying real rows — repaired to version 2 with nothing lost.
- **A key vault stuck at version 1 with no object store could never be repaired.** `openDB(name, 1, ...)` skips `upgrade` when the database is already at version 1, so every later call threw `NotFoundError` and the app could not store a key again, silently. Anything else on the origin calling `indexedDB.open('H3KeyVault')` creates exactly that database; it happened by accident during testing. The vault is now opened without naming a version, with the presence of the object store — not the version number — as the test, bumping only when it is missing. The first attempted fix hardcoded version 1 on reopen and failed the other way with `VersionError`; the regression test caught it.
- **Saving an API key without a passphrase threw and the failure was invisible.** `useEngine` still asked for the retired `device` mode, which `setSecret` had started rejecting, and `saveApiKey` did not catch it, so the form looked like it had saved. The whole unit suite passed while this was broken. `WritableKeyMode` now excludes `device` so `tsc` rejects it at build time, the runtime throw stays as a backstop for untyped callers, and a storage failure is reported in the UI.

- **`connect-src` no longer lists bare `ws:`/`wss:`.** Those are scheme-wide sources matching any host, so they left a compromised dependency a socket to anywhere — the exfiltration route the rest of the policy exists to close. They were there for the Vite hot-reload socket, which `'self'` already covers. Probed both ways against the real policy: before, a `fetch` to an unrelated origin was refused while a `WebSocket` to that same origin went through; after, both are refused, the Gemini endpoint stays reachable, and dev HMR still connects.
- **`frame-ancestors` removed from the `<meta>` CSP.** The directive is ignored there, so it was never doing anything. Noted in the README as needing a response header.

Deliberately narrow — the guide's own summary describes actions, shot count and the ending, and stays green.

## [0.1.0]

First working version: the compiler is complete for all five modes and there is an editor on top of it.

### Added

- **Document model** (`src/core/ir`). Types, zod schemas, path addressing, and the closed vocabularies from both official guides. Slots and subjects are separate registries with a many-to-many between them, because one subject may draw on several assets and one asset may supply several subjects.
- **Normalizer** (`src/core/normalize`). Duration arithmetic including the 17k+5 frame grid, reference label assignment, mode inference from slot roles, and shot/word budgets. Everything computable without a model is computed here and supplied to the planner as fact.
- **Validator** (`src/core/validate`). 51 rules across contract structure, duration, shot numbering and cut times, alignment strings, camera vocabulary, the speaker registry, dialogue and voiceover, cross-cut tags, visible text, the audio sections, Ref2VA labels and retention, and slot ceilings.
- **Source-mapped serializer** (`src/core/serialize`). Both output contracts, with a character range recorded per document path so the rendered prompt links back to the nodes that produced it.
- **Patch pipeline** (`src/core/patch`). Path-scoped edits behind three gates: an allowlist that keeps derived values derived, an existence check that refuses auto-creation, and a guard that makes user-supplied dialogue immutable.
- **Gemini Interactions client** (`src/provider`). One narrow call shape with the API's verified behaviour encoded: `store: false` always, `temperature` never sent, `thinking_level` and `system_instruction` on every call, and a five-way status branch that treats truncation as terminal and distinct from failure.
- **Planner and patch prompts** (`src/provider/prompts`). Shared core plus per-mode blocks, carrying only rules that need semantic judgment.
- **Storage** (`src/db`, `src/crypto`). Five IndexedDB stores and an immutable version tree with branching. API key storage offers a device-derived mode and a passphrase mode, named for what each actually provides.
- **Editor** (`src/ui`). Slot manager with role assignment and derived-label readout, document tree editor, rendered prompt with click-to-select and inline diagnostics, and branch history.

### Verified

- Five golden fixtures reproduce the worked examples from both official guides byte for byte, and all five validate with zero errors.
- Every diagnostic code has a control fixture that makes it fire; a meta-test fails the build if any emitted code lacks one, and that meta-test was itself proven able to go red.
- A purity test keeps `src/core` free of React, the SDK, the database layer, the DOM, and `fetch`.
- 161 tests, clean typecheck, clean production build.

### Notes

- Two API unknowns were settled from the installed SDK types rather than by guessing: `generation_config.thinking_level` is snake_case with values `minimal | low | medium | high`, and `response_format` is `{ type, mime_type, schema }`. Two remain for the live probe script: the model id form and browser CORS.
- Video and audio references are not sent for analysis. Those need a Files API upload with PROCESSING polling and 48h handles; the slots take a written description instead.
